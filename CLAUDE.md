# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

An FTC (FIRST Tech Challenge) robot controller Android project for the 2026-2027 season, forked from the Pedro Pathing Quickstart, which itself tracks the official FTC SDK. Remotes: `origin` = `aevalmere/brocksonix` (the team repo), `upstream` = `Pedro-Pathing/Quickstart`. Builds a single APK that is deployed to the robot's Control Hub.

## Build

Uses the Gradle wrapper (Android Gradle Plugin 8.13, compileSdk 34, Java 8 source level, so no newer Java language features or APIs beyond what Android desugaring provides).

```
./gradlew :TeamCode:assembleDebug        # build the APK
./gradlew :TeamCode:installDebug         # build and install to a connected Control Hub (adb)
./gradlew :TeamCode:testDebugUnitTest    # JUnit tests on the desktop (add --offline when the libraries are cached)
./gradlew :TeamCode:testDebugUnitTest --tests "*ZenithAutoHeadlessTest*" -Dzenith.auto=<auto>   # sim one Zenith auto (see Zenith)
npx -y @horizon36596/zenith-cli@0.1.2 sim <auto> --json   # the same sim, through the Zenith CLI
```

Tests run on the JUnit Platform (SimLoop needs it). The JUnit 4 tests run through the vintage engine, and the sim tests are JUnit 5.

JUnit 4 tests live in `TeamCode/src/test/java/org/firstinspires/ftc/teamcode/agateflow/` (same package as AgateFlow, so they reach its package-private parts; `DriveRouteTest`, `ParkGuardTest` and `EtaCalibrationTest` cover the runtime layer), plus `robot/` (`FireControlTest`, `AimModeTest`), `robot/commands/` (`RetryTest`), `robot/shot/` (`HoodSolverTest`, `MotionPredictorTest`, `ShotSolverTest`, `ShotSolverCoaxTest`), `robot/hardware/` (`CachedHardwareTest`), `field/` (`FieldTest`, `ShootingZoneTest`), `zenith/` (`TeamZenithRobotTest`), `sim/` (SimLoop: `RobotSim`, the mechanism plants, `SimFollower`, `TracedZenithAuto`, and `ZenithAutoHeadlessTest`, which is skipped without `-Dzenith.auto`) and `util/` (`PIDFTest`, `AnglesTest`, `LookupTableTest`, `DriveCurveTest`, `DebouncerTest`, `SeparatingAxisTest`). The AgateFlow tests plan and drive on `TestRobot`, Pedro's real `Follower` and `Foresight` on a simulated drivetrain with a virtual clock (it swaps in `DriveRoute.NOW` and puts back the statics it changes), and check results with their own `TrueRule`. Results go to `TeamCode/build/test-results/`, and pictures of plans to `TeamCode/build/agateflow-svg/`. No linters. Everything else is tested on the robot: the Pedro tuners and the `Tests` procedure (Hold, Line, Curve, Localization, Odometry, etc.).

## Layout

- `FtcRobotController/`: SDK app module. Treat as upstream; don't modify. Its `external/samples` folder holds example OpModes to copy from.
- `TeamCode/`: all team code. `TeamCode/build.gradle` pulls in `build.common.gradle` (shared Android config, don't edit) and `build.dependencies.gradle` (where libraries are added).
- `build.dependencies.gradle`: FTC SDK 12.0.0 artifacts plus Pedro libraries from `https://repo.dairy.foundation/releases/`: `com.pedropathing:revhub` 3.0.1, `com.pedropathing:tuning` 1.0.1, and `com.pedropathing.ivy:pedro` (Ivy command scheduler, 1.1.1); Panels (`com.bylazar:fullpanels` 1.0.18) from `https://mymaven.bylazar.com/releases`; JUnit 4.13.2 for the desktop tests. It also adds JitPack and Zenith's robot runtime (`com.github.Horizon-36596:zenith:v0.1.2`). It applies `TeamCode/simloop.gradle` (SimLoop v0.2.0-alpha.2, JUnit 5, the vintage engine and the platform launcher, all test-only) for the TeamCode project only, since `FtcRobotController` shares the file.
- `zenith.json`, `.mcp.json`, `autos/` (root): Zenith's link file, its MCP server config and the auto files (see Zenith). `deploy` copies the autos to `TeamCode/src/main/assets/autos/`.
- `ROBOT.md` (hardware), `TELEOP_PLAN.md` (controls, warnings, field coordinates), `TUNING_GUIDE.md` (how to measure/tune, by step), `TODO_LIST.md` (generated, see below), `RUNDOWN.md` (how the code runs, for students: one Main TeleOp loop, `Robot.update()` step by step, every auto command), `SOFTWARE_INNOVATIONS.md` (what is new in our software and how it works, for judges). Which doc a change goes in: Docs, below.

## Docs

Any change to code, buttons, hardware or tuning updates the doc that owns it, in the same change:
- Hardware: `ROBOT.md`. Buttons, driver warnings and field coordinates: `TELEOP_PLAN.md`. Measuring and tuning, by step: `TUNING_GUIDE.md`.
- How the code runs: `RUNDOWN.md`. What is new, for judges: `SOFTWARE_INNOVATIONS.md`. Design notes: the comment at the top of each class, not a separate doc. Rules for agents: this file.
- Docs name classes and methods (`Robot.update()`, `FireControl`'s WAIT step), never line numbers: they go stale with the next edit.
- `TODO_LIST.md` is generated (see the TODO rule below). `README.md` is the FTC SDK's own: leave it.
- Don't add review, report or session-summary `.md` files to the repo. Put them in `.claude/` (git-ignored) or a scratch folder.

## Robot code (`teamcode/`)

`teamcode/` is `TeamCode/src/main/java/org/firstinspires/ftc/teamcode/`. Every folder, sub-folders included, is its own Java package:

- `opmodes/`: only OpModes (what the Driver Station lists): `teleop/` (`MainTeleOp`), `auto/` (`AutoTemplate`), `auto/zenith/generated/` (OpModes Zenith writes; never hand-edit), `test/`. Test OpModes build single subsystems instead of `Robot`. `Drive Test` builds only Pedro's `Mecanum` and `PinpointLocalizer` from the `Constants` configs, so it runs before any tuning. Its D-pad spins one wheel alone, which must roll the robot intake first; Cross switches it between robot-centric and field-centric (`Drive.driverToField`, the rotation `Drive.drive` uses). `DriveTest.stickPowers` negates the sticks like Main TeleOp (stick up reads -1), so a wrong drive direction is fixed in the `Constants.drivetrainConfig` motor directions, never in the stick signs. `Intake Test` also drives robot-centric with Drive Test's stick code (`DriveTest.stickPowers`), so it needs the four drive motors plus `intake`: it builds the real `Intake` subsystem, runs it from Start, stops it while the optional `beamFull` reads full, and LT reverses it.
- `driver/`: what the drivers see and feel, used by the match OpModes. `AllianceSelector` picks the alliance in init. `Feedback` runs the gamepad rumble and light; the light is gamepad1 only. It has three rumbles. Warning (gamepad1): 3 strong pulses when a warning appears (`OUT_OF_RANGE` is screen-only). Full (gamepad1): a soft constant rumble while storage is full. Relocalized (both gamepads): one strong pulse (`RELOCALIZE_MS`) from `Feedback.relocalized()`; gamepad1 gets it after any warning buzz that is already playing.
- `robot/`: the robot itself. `Robot` owns all subsystems and holds the per-loop decision logic in `update()` (`Robot(HardwareMap)` calls `Robot(HardwareMap, Follower)`, the seam the sim uses to hand in a simulated follower); OpModes only map buttons (TeleOp) or schedule commands (auto) onto it. Nothing fires without an alliance and a trusted pose (`Robot.canFire()`).
  - Nothing writes a motor or servo during INIT (G304.H, G403); everything moves in the first loop after Start. R503 allows 8 motors and 8 servos: this robot uses 8 motors and 4 servos (5 with the coax hood, the CR turret servo counted as a servo). No endgame timer: TELEOP is 2:00 with no named ENDGAME.
  - The flower intake goes up at Start, then moves only when told: driver 1's LB toggle in TeleOp, commands in auto (`RobotCommands.withFlowerIntake`, `flowerDown`, `flowerUp`, `parkGuard`). `Robot.update()` only writes the position it was last given; full storage doesn't raise it.
  - `FireControl` runs continuous fire. A burst starts with enough balls once the shot (`Robot.aimed()` and `Robot.wheelReady()`) stays ready for `READY_HOLD_MS`; the door opens and the rail starts when the door is fully open, then runs at `ShotTables.SHOT_FEED_POWER` / `PASS_FEED_POWER` (by distance) while the button is held, so that feed power sets the fire rate. Mid-burst the wheel's sag is expected: the rail pauses (door open) only while not aimed or while the wheel is more than `BURST_RPM_FLOOR` under target. Letting go stops the rail at once, and the door closes `DOOR_CLOSE_DELAY_MS` later; a shoot/pass switch mid-burst closes the burst the same way. The shot counter (an RPM drop of `SHOT_DIP_RPM` from the highest reading of the last `DIP_WINDOW_MS`, one count per dip) only reports shots, to telemetry and `Robot.shotsFired()`. It moves the rail only with `Robot.stopAfterOneShot` (auto's `RobotCommands.shoot()`, which holds shoot until one shot is counted). `NO_SHOT_WARN_MS` only adds a note to the Fire telemetry line. `shootAll` and `shootContinuous` keep shoot held `RobotCommands.LAST_BALL_MS` after storage reads empty, since letting go stops the rail at once.
  - Shoot or pass is decided in `Robot.update()`, not by a button: `Robot.decideAimMode(upCell, half, FireControl.PASS_ENABLED)`, every loop, fire held or not, so the wheel already spins for a pass. `Robot.upCell` is null until driver 2 picks it (LB/RB, `Field.cellFromDriver`, the cell on the driver's left/right); auto never sets it. The robot's half is `Field.cellForSide` (6 in. band). No up cell, or on its half: SHOOT at the cell on the robot's half. On the other half: PASS to `Field.passTarget(alliance, half)` (the target on the robot's own half), or NONE with `PASS_ENABLED` false. Passing is on, with the static hood's `PASS_RPM` / `PASS_FEED_POWER` still placeholders (`TODO(7)`, G405: no ball may leave the field). `Robot.passHeld` no longer exists.
  - Zone fire: `Robot.zoneFire` (driver 1's Triangle; off in every new `Robot`). While any part of the robot's outline (AgateFlow's `ROBOT_FRONT` / `ROBOT_BACK` / `ROBOT_HALF_WIDTH` rectangle) overlaps `field/ShootingZone` (a trapezoid in front of the up cell, else the cell on the robot's half; `util/SeparatingAxis` is the overlap test) and `canFire()` is true, it fires as if `shootHeld` were set. Leaving the zone stops the rail at once (the CLOSE step) unless `shootHeld`. Parked in the zone, the rail keeps feeding, on purpose. `Robot.goalStatus()` and `zoneFireStatus()` are Driver Station lines, shown with `FULL_TELEMETRY` off too; the zone drawing is Panels-only.
  - Relocalize is driver 2's: `Robot.relocalize(Corner)` (4 corners: `NEAR_*` on our alliance wall, `FAR_*` on the other; trusts the pose, resets all trims) and `Robot.relocalizeHeading(leftWall)` (heading only, from `Field.sideWallHeading`; keeps x, y and the trust flag, resets the turret trim, refused while the pose is NaN). Both return whether they ran, and `MainTeleOp` then calls `Feedback.relocalized()`. Driver 2's sticks trim at a rate per second: left X the turret, right Y the RPM (the hood while `usingCoaxHood()`).
  - `Warning` enum plus `Robot.warnings()` is the single source for driver warnings. Telemetry prints them and `Feedback` buzzes. `Warning` stays next to `Robot`, not in `driver/`, so a new warning is added in one folder and `robot/` never depends on `driver/`.
  - The `Shooter` and `Turret` watchdogs latch off until the OpMode restarts (`SHOOTER_OFF` / `TURRET_OFF` warnings). The turret's stuck check first tests (pushes harder to rule out friction), then rests and retries, and latches only after 3 failed tests in a row, so a turret that is held for a few seconds comes back. Under `KS` it cuts the push to 0 once the angle stands still, so an encoder that freezes mid-move can't leave the turret creeping. Wrong `REVERSED` flags are caught by the wrong-way check (the turret turns against its own push), within about 1.5 s (about a third of a second when the target is near) even while the robot turns; the full-power check stays as a backup.
  - A NaN pose blocks aiming. A burst that is already firing pauses its rail (not aimed) but keeps the last good RPM, turret target and feed power, so a ball already past the door isn't ruined.
  - Two hoods, picked live by `Robot.HOOD` (`HoodType`, Panels page "Robot"), switched only between bursts (a switch resets the RPM and hood trims). `STATIC`: fixed launch angle, `ShotTables.SHOT_RPM`; aimed needs a fitted coax hood's `atTarget()`, and the wheel is ready at `Shooter.atSpeed()`. `COAX`: `subsystems/CoaxHood` (positional servo, gear ratio TBD, no position feedback, so it estimates arrival from `SPEED_DEG_PER_SEC`); the wheel targets `ShotTables.COAX_RPM` and `shot/HoodSolver` solves the launch angle every loop from `Shooter.averageRpm()` (GNCE Ditto's idea), so aimed needs a scoring angle (one that still scores `HoodSolver.RPM_MARGIN` either side of the reading) and the hood at it (`coaxHood.update()` runs before the check so the estimate counts this loop's move), and the wheel is ready within `Robot.COAX_RPM_TOLERANCE` of target. The `hood` servo is optional in the configuration: `Robot.coaxHood` is null without it, and `COAX` then falls back to `STATIC` with the `HOOD_MISSING` warning. With the coax hood on and `STATIC` picked, it holds `CoaxHood.STATIC_LAUNCH_DEG` so the static tables still fit. A mapping that needs a servo position past 0 to 1 raises `HOOD_AT_END` (`CoaxHood.servoAtEnd()`). While the coax hood shoots (`Robot.usingCoaxHood()`), driver 2's right stick Y trims the hood instead of the RPM. Launch angles are degrees above horizontal everywhere.
  - `RobotState` carries the alliance, target cell and pose from one OpMode to the next. `Robot.update()` saves the pose only when it is trusted and not NaN. Switching alliance in init drops the saved pose, since it is in the other alliance's frame.
  - `subsystems/`: one class per mechanism, each with `addTelemetry()`. Most take a `HardwareMap`, work on their own, and have `update()` (reads/writes hardware). Exceptions: `Drive` takes a Pedro `Follower`; `Intake` (intake motor, slots 3-4) and `Transfer` (transfer motor, slots 1-2) have no `update()` and write inside `collect`, `feed`, `reverse` and `stop`, and `Robot` calls both in the same branch; `Shooter` and `Turret` also take a `VoltageCache` (`Robot.voltage`); `CoaxHood` is only built when `CoaxHood.isConfigured(hardwareMap)`.
  - `commands/`: Ivy commands for autonomous, `RobotCommands` and `Retry` (see Architecture). AgateFlow's commands are in `agateflow/`.
  - `shot/`: `ShotSolver` (aim + RPM, layered SOTM with on/off switches; `solveCoaxShot` for the coax hood, where `LEAD` uses physics flight time; `PREDICT` solves the shot from the pose at release, `RELEASE_LATENCY_SEC`, and aims the turret from the pose at `TURRET_LATENCY_SEC`, via `MotionPredictor`: lag-compensated velocity, one-step smoothed acceleration, stop-clamped, ported from GNCE Ditto's final ShotPlanner, which `HoodSolver` also credits with links pinned to their last commit), `ShotTables` (distance lookup tables, plus `COAX_RPM`, and `COAX_EXIT_SPEED` / `COAX_EXIT_SPEED_ANGLE`, keyed by RPM and by launch angle) and `HoodSolver` (pure projectile physics, desktop-tested in `TeamCode/src/test/.../robot/shot/`).
  - `hardware/`: hardware access. `HardwareNames` (configuration names), `BulkReads`, `CachedMotor` / `CachedServo` / `CachedCRServo` (write only on change; `raw()` clears the write cache, so the next write always goes out), `VoltageCache`. Keep writes cached, call `BulkReads.clear()` once per loop, and never read motor current in the match loop.
- `agateflow/`: AgateFlow, the on-the-fly path planner, built but not used by any match OpMode yet. `Route` (chain of `to`/`through` waypoints, written for red) goes into `AgateFlow.plan`, which returns a `Plan` of `Leg`s, one Pedro `Path` per stop.
  - How it works: visibility graph around `Zone`s grown by the robot radius, then `CornerCurve` G2 corners, then `MotionModel` simulates Foresight (its look-ahead cuts inside curves, gains read from the follower) on the `DriveModel` physics in 10 ms steps, with battery sag. Speed-limit Modifiers (`maxVelocityConstraint`) go where the predicted path would get too close. It picks the fastest safe candidate. If none keeps the whole `SAFETY_MARGIN`, it takes the quickest one that misses by less than `NEAR_MISS_FRACTION` of it and still clears `ROBOT_RADIUS`, with a note in the `Plan`. Each class's top comment has the details.
  - The robot is its outline (`ROBOT_FRONT`, `ROBOT_BACK`, `ROBOT_HALF_WIDTH` around the turret center), checked on both the planned and the predicted path. Any part may touch the 4 field walls (`WALL_GAP`, 0), but never moves into one faster than `WALL_CONTACT_SPEED`. Along a path every other zone keeps `SAFETY_MARGIN` from the whole outline; near the start and end the robot may come into the margin, but its outline never goes into a zone or a wall (except the flower intake reaching into a FLOWER's opening on purpose, `Route.allowContact()` stretches, which use the `CONTACT_RADIUS` circle, and a start that already overlaps). Where the robot doesn't fit, AgateFlow says so in the `Plan` notes: it moves a waypoint with its own heading until the outline is 0.5 in. clear, leaves out a pickUp target it can't reach (`Plan.skipped()`), and refuses a turn in place that would swing a corner into something. A waypoint without a heading (`to(x, y)`) may arrive side-on or backward if that fits. Next to a wall it may keep its start heading for up to `MAX_START_HOLD` in., or finish a turn up to `MAX_END_HOLD` in. before a waypoint. AgateFlow never changes a heading the route asks for, and a fixed or linear heading crosses gaps at an angle (wider across the path), so tight places want `Heading.tangent()`, no heading, or a through-waypoint before the gap.
  - `Route.pickUp(poses)` (`.most(n)`, `.inOrder()`, `pickUpLive`) drives over floor targets intake first, in the fastest order (every order up to 7 groups; beyond that Held-Karp gives a near-best one, usually the best, under 10% off at worst; see `Pickup`). `Plan.pickedUp()` / `skipped()` say which it gets.
  - `Route.flowerIntakeDown()` plans that stretch with the front at `IntakePoses.FLOWER_INTAKE_REACH`. `RobotCommands.withFlowerIntake(drive)` lowers and raises the intake to match (`DriveRoute.flowerIntakeDown()`). Every other stretch is planned with it up, except the first `FLOWER_INTAKE_RAISE_RUN` in. after a down stretch, while it comes up (the robot backs straight out and keeps its heading there). Between drives, `RobotCommands.flowerUp()` raises it and waits `FLOWER_RAISE_MS`.
  - `FieldMap` holds zones by source: walls always, `FieldZones` (the HIVE frame ends and the 4 FLOWERS), and vision via `setZones("vision", ...)`, which is safe from a camera thread and drops null or NaN zones.
  - `AgateFlowCommands.driveTo(route)` gives an Ivy `DriveRoute`. It plans on a background thread and replans when pushed, or when new zones take room from the path ahead. Near a stop, where it's meant to get close, only a new zone that leaves less than `ROBOT_RADIUS` counts, so a partner parked on a stop makes it replan, and the replan moves the stop out of the zone (or leaves out a pickup it can't reach). Every loop while the zones differ from the plan's, it checks the predicted path 30 in. ahead (along the path): a new zone there makes it brake straight against its motion (`STOP_BRAKING_POWER`) until nearly still, hold, and replan from there. A replan that comes back after the robot moved on to the next leg is dropped. A replan within `FLOWER_INTAKE_RAISE_RUN` of a `flowerIntakeDown()` stop still starts with the intake coming up (`Route.startingFlowerDown`). It gives up `TIMEOUT_SCALE` x its first estimate + `TIMEOUT_EXTRA_SECONDS` after the first plan; replans can add at most `REPLAN_EXTRA_SECONDS` more, except a detour around a new zone, which gets its own plan's time (at most `MAX_DETOURS` times; `DriveRouteTest` checks both). A robot still getting closer at the deadline gets up to `MAX_OVERTIME_SECONDS` more; progress starts over with each new plan. `EtaCalibration` learns real/predicted time (smoothed by `LEARN_FILTER`) only from legs driven start to finish on their own plan that reached their stop: not the first leg of a replan, a leg it gave up settling on, or a `driveTo(estimate)` leg joined partway. `DriveRoute.NOW` is the clock, swapped for a virtual one in the tests.
  - `Route.toLive` suppliers are asked on the main thread (in `AgateFlowCommands.planLater`) at the start, every replan and every estimate, never on the planning thread. Live poses are field coordinates, but a `Heading` (like `facing`) is always written for red.
  - `AgateFlowCommands.estimate(route)` times a route in the background without driving it. `driveTo(estimate)` starts with that plan, without waiting, only while it still fits: the robot is within 1 in. and 5° of where the estimate was made, or the estimate is under 0.5 s old and the robot is on its predicted path. Otherwise it plans again. It replans while driving like any `DriveRoute`.
  - `ParkGuard`: call `update()` each auto loop before `Scheduler.execute()`. When the time left reaches the current park estimate plus a margin, it schedules the park drive at high priority, requiring every subsystem passed in, which interrupts whatever auto command is running. Whenever the park command isn't scheduled and hasn't arrived (no plan, timed out, interrupted, or never let start), it starts it again while more than 0.5 s is left. Its estimates wait while a `DriveRoute` plan is pending, so drive plans never queue behind them. Build it with `RobotCommands.parkGuard(...)`, which passes every subsystem, holds the flower intake up for the whole park drive (AgateFlow sizes the robot with it up), and passes `robot.flowerIntake::isDown` to `ParkGuard.flowerIntakeDown`, so parking from a FLOWER plans the back-out with the intake coming up. Known gap: `isDown()` is the command, not the servo, so a retry within `FLOWER_RAISE_MS` of the first start plans with the intake up.
  - It never produces hairpins (Foresight can stick on them): a through-waypoint that needs one becomes a stop, with a note in the `Plan`.
  - `PlanDrawing.toPanels(plan, map, pose)` draws zones, the planned path, the predicted path, robot outlines and pickups on the Panels field page (PEDRO_PATHING preset). It sends by itself, at most every 100 ms. Its `TO_PANELS` (144 / `Field.SIZE`) is for drawing only; planning never uses 144. `toSvg` is for the tests.
  - `DriverAssist`: one-button TeleOp drive along a `Route`; the sticks take over at once. Not in `MainTeleOp`.
  - The `AgateFlow Benchmark` test OpMode (`opmodes/test/`) times planning on the Control Hub without moving, then shows each plan on Panels (D-pad picks it).
  - Validation is desktop-only so far: the JUnit tests, plus random fields against Pedro's real `Foresight` in closed loop on a simulated drivetrain. It has not run on the robot.
  - One package on purpose: Java's package-private access only works inside one package, and a sub-folder is a separate package. `VisibilityGraph`, `ClearanceRule`, `MotionModel`, `Track` and `Geometry` are internal, and `Route`, `Waypoint`, `Heading`, `Zone`, `Leg` and `Estimate` have package-private parts. `AgateFlowCommands`, `DriveRoute` and `ParkGuard` use those parts, so they stay here, not in `robot/commands/`. Don't make internals public just to split the folder.
- `zenith/`: the bridge to Zenith (see Zenith). `TeamZenithRobot` is Zenith's robot interface over our `Robot`, `ZenithAuto` is the base class of the generated OpModes, `ZenithFrame` moves poses between Zenith's centre-origin frame and ours.
- `field/`: field coordinates in inches, Pedro frame: origin at the red-wall/audience-wall corner, +x toward blue, +y away from the audience. Write poses for red; `Alliance.fromRed` flips them for blue (180° spin about the center). `FieldZones` (AgateFlow's keep-out zones) and `IntakePoses` (auto pickup spots) are here too. `ShootingZone` is zone fire's trapezoid (`@Configurable`, Panels page "ShootingZone"; corners written for red with the FAR cell up, mirrored for the AUDIENCE cell and for blue, not spun). `Corner` names the 4 relocalize corners (`Field.cornerPose`), and `Field.sideWallHeading` gives the side-wall headings.
- `pedro/`: Pedro Pathing setup and tuners (see Architecture).
- `util/`: plain helpers with no hardware: `Angles`, `LookupTable`, `Debouncer`, `DriveCurve` (stick shaping), `SeparatingAxis` (do two convex shapes overlap, for `ShootingZone`), `PIDF` (our own controller, used by `Turret`: I with zone, cap, anti-windup and resets; D on measurement; smoothed, capped target-rate feedforward), `PanelsSettings` (`EVENT_BUILD` keeps Panels off in event builds, see Panels below). Every smoothing knob in the code runs the same way: 0 = none, closer to 1 = smoother, through the one helper `PIDF.smooth`.
- Panels: every tunable is a non-final `public static` field in a `@Configurable` class and must take effect live. Never read one only in a constructor, and apply direction flags when writing the power or position, not with `setDirection`. The shot tables (Panels edits values, not row counts; distances must stay increasing), `MainTeleOp`, `ShootingZone` and the auto poses are in Panels too. Copy final values back into the code, since edits are lost on app restart. A Panels page is named after its class (not its folder), so renaming a `@Configurable` class renames its page. Panels is for practice only: Competition Manual R704.D (2026-27) prohibits FTControl Panels at events, with no "during MATCH play" limit, so a match OpMode must never need Panels for a value or for driver info (warnings go to Driver Station telemetry). Panels turns itself back on at every app start unless `util/PanelsSettings.EVENT_BUILD` is true. That is the switch for event builds: set it true before installing for an event, and back to false after.
- Anything that needs measuring or tuning gets a `// TODO(step): what to do` comment right above it, in exactly that form (anything else, like `// TODO: x`, is left out of the list with a build warning). The step is the `TUNING_GUIDE.md` section number, 1 to 16, numbered in order of importance and grouped into phases: 1-8 TeleOp bare minimum, 9-10 first autonomous and before competition, 11-12 make it better (shooting while moving, driver feel), 13-15 AgateFlow and auto pickups, 16 the coax hood (once it is on the robot). Pick the step by when the item is needed, not by which class it is in (a `DriveModel` field is 13, except `TUNED_VOLTS`, which must be read during step 2). An unknown step number gets a build warning too. The `todoList` Gradle task (runs before every build) regenerates `TODO_LIST.md` from these. Don't edit `TODO_LIST.md` by hand.
- Code style: written for students to read. Plain names, short comments only where the why isn't obvious, no clever abstractions.

## Architecture

**OpModes** are discovered by annotation (`@TeleOp` / `@Autonomous`) via the SDK's annotation processor; no registration needed. Use `LinearOpMode` with a `while (opModeIsActive())` loop. Match OpModes use `driver/AllianceSelector` in init. Right after init, call `resetEdgeDetection()` on each gamepad the loop reads (`MainTeleOp` and every test OpMode do), or a `...WasPressed()` press made during init fires on the first loop.

**Pedro Pathing 3.x (`teamcode/pedro/`)**
- Upstream's files: `Constants.java`, `Tuning.java` (an empty class; leave it alone) and every tuner in `procedures/` except `DriveModelTuner`. Keep their paths and names, or every upstream merge conflicts. `TeamTuning` and `DriveModelTuner` are ours.
- `Constants.create(HardwareMap)` is the single factory that builds the `Follower` from three parts: a `Drivetrain`, a `Localizer`, and the path-following `Algorithm` (Foresight). `Constants` holds starting `drivetrainConfig` (`MecanumConfig`) and `localizerConfig` (`PinpointConfig`) values in the form MecanumTuner and PinpointTuner print, so their output replaces them as is. `create()` still returns `null` until the ForesightTuner output is in as `foresightConfig()`. Until then `Robot` throws a clear error at init.
  - The ForesightTuner output goes in a `foresightConfig()` method that builds a new `ForesightConfig` on every call, not in a `static` field (the comment in `Constants` shows how). A path's speed-limit `Modifier` writes into the config and is only put back when the follower lets go of the path, so a shared config could keep a limit after an OpMode stops mid-path or crashes.
- Tuners are registered in `TeamTuning.java`: the tuning menu scans every class under `org.firstinspires.ftc.teamcode` for static no-arg `@Tuner` methods returning `Procedure`. `MecanumTuner`, `PinpointTuner` and `ForesightTuner` are registered (run ForesightTuner after the first two outputs are pasted into `Constants`). `Tests` gets added after the Foresight output is too (the code to add is in a comment).
- `procedures/` contains the tuners. Each is a `com.pedropathing.tuning.autotune.Procedure` whose `run()` drives an interactive flow (`inputs(...)`/`awaitInputs`, `confirmation`, `runOpMode(new SomeTuningOpMode(...))`, `result`, `abort`) and ends by emitting a Java snippet via `code(Language.JAVA, ...)` to paste into `Constants`. Individual robot motions are package-private `TuningOpMode<T>` subclasses in the same file that return the measured value.
  - Hardware setup tuners (`MecanumTuner`, `PinpointTuner`, `OTOSTuner`, `OctoQuadTuner`, `TwoWheelTuner`, `ThreeWheelTuner`, `ThreeWheelIMUTuner`) take no constructor args.
  - `ForesightTuner`, `DriveModelTuner` and `Tests` take `Function<HardwareMap, Localizer>` / `Function<HardwareMap, Drivetrain>` (and `Tests` a `Supplier<Algorithm>`) so they can run before a full `Follower` exists; `Tests` builds a `Follower` only when all three are non-null. `DriveModelTuner` (ours) measures the numbers `agateflow/DriveModel` needs; it emits code for `DriveModel`, not `Constants`.
  - Tuners must keep commanding drive powers every loop iteration (not set once) so they work with swerve drivetrains, and use `Thread.sleep` pauses between phases to let the robot settle.

**Ivy (`robot/commands/`)**: used for autonomous only.
- `RobotCommands` builds commands that set what `Robot` should do (`shootHeld`, `unjamHeld`, `flowerIntake.setDown`, `singleBallBursts`, `stopAfterOneShot`) and wait on what it reports. They never drive hardware directly. `withFlowerIntake(drive)` runs an AgateFlow drive with the flower intake following its plan.
- `Retry` reruns a command while a check fails, up to a limit (`shootAllWithRetry` uses it). It ends each try exactly once, so use it instead of building retries out of Ivy groups.
- The auto loop is `Scheduler.execute()`, then `robot.update()`. `Scheduler` is static, so call `Scheduler.reset()` first. After the loop, call `robot.stop()`: it stops the follower, so Pedro puts back any path speed limit.
- `AutoTemplate` (`@Disabled`) is the skeleton to copy. Its poses are written for red; `Robot.setStartPose` and `driveTo` flip them for blue.
- TeleOp does not use commands. Its loop still runs buttons, then `Scheduler.execute()`, then `robot.update()`, as in auto, so one-button macros can be added later. `driverOne` sets `shootHeld` and `unjamHeld` from the buttons every loop, so a macro that sets one of them must be OR-ed in there. `zoneFire` is flipped by a press, not set every loop.
- Ivy 1.1.1 gotchas:
  - Groups can call `end()` on a child that never started, or twice, so cleanup in `setEnd` must be safe to repeat (see `RobotCommands.stopShooting`).
  - Scheduling a second top-level command that shares a requirement cancels the one already running, so keep a routine in one `sequential(...)`.
  - `Command.unless()` never finishes (it uses `NOOP`). Avoid it.
  - `Scheduler.reset()` does not call `end()`.
  - `PedroCommands.follow` has no `end()`, so a cancelled follow keeps driving. Hold on interrupt, as `RobotCommands.follow`, `driveTo` and `DriveRoute` do.
  - Pedro never times out a follow, so every auto drive needs a limit (`driveTo(pose, ms)` or AgateFlow's deadline).
  - `.requiring(...)` replaces a command's requirements, including a group's union.
  - `waitMs` uses the wall clock.
  - `hold(follower)` reads the pose when the command is built, not when it runs.

## Zenith

Zenith (Horizon 36596, 0.1.2) is a desktop tool that writes autos as `autos/*.auto.json` files, and a small runtime that plays them through Ivy. SimLoop is their headless simulator. Both are Horizon 36596's work. Our part is `teamcode/zenith/` and the sim code in `src/test/.../sim/`. Versions are pinned (`.mcp.json`, the CLI commands, `build.dependencies.gradle`) because the formats may change before 1.0. `.mcp.json` runs `@horizon36596/zenith-mcp@0.1.2` (51 tools); it shows up only after a Claude Code restart and approval of the project server. The CLI is `npx -y @horizon36596/zenith-cli@0.1.2 <verb>`; there is no package.json.

- Loop: edit the auto file, `validate`, `render` (a picture, into the git-ignored `autos/.renders/`), `sim`, then `deploy`. A sim run takes about 10 s and reads `autos/` directly, so edit and re-sim without deploying. Blue: `ZENITH_ALLIANCE=BLUE` or `-Dzenith.alliance=BLUE`. The trace goes to `TeamCode/build/sim/<auto>.trace.json`. `deploy` copies the autos to `TeamCode/src/main/assets/autos/` and writes OpModes into `opmodes/auto/zenith/generated/` (config in `zenith.json`; `deploy.opModeBase` is `ZenithAuto`).
- Frame: auto files are centre-origin and written for red. A red pose (x, y, h) in our `Field` frame is (x - 70.75, y - 70.75, h) in a file (`ZenithFrame`). `ZenithAuto` shifts by `Field.SIZE / 2` and mirrors once for blue (`Alliance.BLUE.fromRed`). It sets the start with `Robot.setPose(pose, true)`, not `setStartPose`, which would flip it twice. `autos/field/biobuzz.field.json` is converted from Zenith's 144 in. field (walls at ±72) to ours: `sizeIn` 141.5 (`Field.SIZE`), walls at ±70.75, and the FLOWER feet, wall brackets and rings, GARDEN POLLEN and LOADING ZONES measured from those walls with the same numbers as `Field`, `FieldZones` and `IntakePoses`. HIVE objects are measured from the centre and unchanged. Which source wins (Field Acceptance Checklist, then the field CAD, then the manual; within 0.1 in. ours stays) is in `Field`'s class comment and `TELEOP_PLAN.md`, Field coordinates. A newer upstream field file must be converted from 144 the same way before use: changing `sizeIn` alone leaves its wall objects 1.25 in. through our walls.
- Loop order: `ZenithAuto` runs `periodic` (empty), `Scheduler.execute()`, then `afterLoop` (`robot.update()`), so `follower.update()` runs once. `onStop` calls `robot.stop()`. No alliance picked in init: it sits still with a warning. Changing the alliance in init rebuilds the routine.
- Named commands (`TeamZenithRobot`): `shoot`, `shootAll`, `shootAllWithRetry`, `shootContinuous`, `flowerDown`, `flowerUp`, `waitUntilFull` (`timeoutMs`), `unjam` (`ms`). `shootContinuous` never ends by itself: use it only in a parallel step with a path as the deadline. Conditions: `storageEmpty`, `storageFull`, `canFire`. A path's `atSpeed` sets Foresight's `maxPathSpeed` for that path.
- No markers: a path step with markers is refused at init. Zenith's marker runner calls `Follower.curveCompletion()`, which Pedro 3.0.1 lacks (found by a bytecode check of the library against Pedro). Use a parallel step with the path as its deadline. After a version bump, run that link check again.
- Timeouts: a path with no `timeoutS` gets `TeamZenithRobot.PATH_TIMEOUT_SECONDS` (6, `TODO(9)`) divided by the speed fraction. Pedro never times out a follow, so every path needs one.
- Sim limits: exact localizer, placeholder plant constants (`TODO(step)`s live in `src/test`, so `todoList` doesn't list them), no battery sag, no field contact, no `hood` servo (runs `HOOD=STATIC`), `TestRobot` drives at 70 in/s while `robot.json` says 85. Sim time drives Ivy `waitMs`, `ElapsedTime` and `DriveRoute.NOW`; AgateFlow's planner thread still runs in real time. It has never been compared with the real robot, so a sim time is not a promise.
- `autos/robot.json`: footprint, speeds and accelerations are APPROX or PLACEHOLDER (CAD and `DriveModel` fallbacks) until measured; each value's `provenance` says which. `zenith calibrate --write` labels results "CALIBRATED FROM SIM"; relabel to "CALIBRATED FROM ROBOT" only for real robot traces.
- Bump: change the version in `.mcp.json`, the CLI commands, `build.dependencies.gradle` and this file together. Then convert any newer field file from 144 (see Frame), re-run the Pedro link check, and run all the gates.
- GitHub: `zenith propose` (commit to `auto/<auto>/<login>`, push, PR) only when the user asks, like any push. It has no sign-in yet (no `gh`, no `GH_TOKEN`).
- Later, not started: combine with AgateFlow. In order: an `agateDrive` named command around `AgateFlowCommands.driveTo`, so SimLoop sims AgateFlow end to end (first, the sim needs a way to plan on the calling thread, since SimLoop doesn't step `AgateFlowCommands.WORKER`); a desktop test that checks the field file and `robot.json` against `FieldZones` and AgateFlow's numbers; then Zenith's optimizer as an offline yardstick for AgateFlow's routes. Zenith's optimizer and sim are desktop TypeScript (13 to 19 s per path step), so neither runs on the robot. Exporting AgateFlow plans to Zenith files loses its degree-5 corners and per-stretch speed limits: not worth it.
